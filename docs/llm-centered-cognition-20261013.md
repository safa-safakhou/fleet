# LLM-centered memory, reflection and plans — 13 October 2026

Founder authorized implementing the researched LLM-centered approach in Fleet: memory, reflection, persistent plans and beliefs about other players, with VW unused, no new accounts/comparison and Laya used only in a demonstrated supporting role. Codex completed source implementation and synthetic/local acceptance without delegation. This is not a live rollout, model-weight learning or certification of human-like gameplay.

## Delivered

Fresh configuration offers `cognition: "llm-centered-v1"`, optionally `recallAssist: "laya-recall-v1"`. Owner values and the original LLM retain strategic judgment. Observed episodes, persistent intentions and uncertain social hypotheses enter future decisions; concise updates return alongside the normal action/read/wait within the same calls/tokens/turn deadline. The LLM can retain, revise, wait on or abandon plans according to evidence and its values. The controller does not impose fixed strategic focuses, forced communications or building/contact rewards.

New game-independent cognition/recall ports and additive `006_cognition.sql` store encrypted, owner-scoped evidence, state and idempotent updates. PACT-specific observation/peer extraction stays in its adapter. Actual messages, agreements, owned observations and command receipts are labeled separately from model interpretations. Required evidence must actually be delivered and still belong to this agent; fabricated/foreign/expired references, unobserved peers, self-corroboration by interpretation, stale versions and conflicting updates are refused. Known model usage precedes cognitive writes. Pauses fence late updates. Unknown usage and uncertain commands keep original reservations/IDs and recovery gates; no committed memory is fabricated for an uncertain submission.

Recall uses relevance, peer relevance, recency and importance, with current facts and recent receipts prioritized. Plans survive restarts and unrelated updates. Predictions and alternatives let the LLM revise a belief after contrary evidence; assessments/confidence remain subjective, with no automatic assertion of another player's true motive. `fleet_memory_recall` supplies additional own-history evidence through the existing bounded read/decision flow. Input reduction explicitly marks missing recall, preserves the plan and authoritative/requested-read priorities, and admits citations only from actual delivered evidence, including a delivered own-memory read.

Storage is bounded: 200 episodes per agent, with retention of current entries, evidence anchors, recent experiences and important episodes. Individual plans/beliefs/reflections and episode/update bodies expire after 30 days without their own refresh. Source expiry/eviction is disclosed. Cognitive detail in the inspector requires the existing observation consent. The inspector displays readable plan/status/steps, hypotheses/alternatives/predictions, reflections and an evidence disclosure. Turn events distinguish delivered continuity, accepted revisions and exact update/fallback failures. See [the operational contract](cognition.md) for schemas, limits, privacy, setup and recovery.

VW is disconnected from runtime construction, removed from new configuration choices and refused by new `Store.configure` selections. Existing legacy source/journal fields and historical tests/evidence are retained; no historical row was reset. Existing LLM-only configurations keep their original output schema. HTTP and Codex preserve the optional cognition update for controller validation. No authoritative gameplay formula or second permission system was introduced.

## Laya evidence and deliberately narrow role

Installed open-source checkpoint: **`convaiinnovations/laya-typed-decisions`**, exact revision **`e929ae5cf69bc34259cd2f95c9e91145b818b1f0`**, using **Laya 0.4.6 / Python 3.12.13**, CPU/two threads and a fully pinned Python dependency lock. Its only runtime purpose is selective ordering of **two already retrieved memory candidates**. It does not choose commands, priorities, plans, beliefs, permissions or weights. Both candidates remain available to the LLM; current observation/receipt priority is preserved. Unavailable, invalid, timed-out and uncertain results retain deterministic recall with an explicit reason.

Actual evaluation history is retained rather than hiding the failed candidates:

1. Frozen initial 12-case semantic-recall diagnostic, both option orders: **21/24 correct**, failing the all-correct gate. Construction-material and exchange cases exposed errors. Original protected artifact: `laya-recall-initial.json` under this Mac's existing private Fleet root.
2. A selective 0.75 cutoff, fixed before the next 16-case set: **5/32 accepted, 5/5 correct**, failing its minimum-coverage gate. That result became development evidence, not deployment acceptance. Protected artifact: `laya-recall-selective-initial.json`.
3. A revised **0.65 abstention cutoff and minimum 25% coverage** were fixed before evaluating another separately frozen 16-case validation set. Final: **18 accepted / 18 correct / 14 abstained, 32 predictions in both option orders**, versus **8/18 correct** for lexical ordering on the same accepted cases. Raw unfiltered correctness was **28/32**; the four wrong raw answers were not accepted. The 28 development cases also had zero accepted errors. Final verification took **4,981 ms** for the validation plus development checks on this Mac. Public artifact: [`laya-service/acceptance.json`](../laya-service/acceptance.json); reproducible sources are the three frozen JSON fixture sets and diagnostic/selective scripts.
4. The actual loopback server and TypeScript client reproduced **18 accepted/correct + 14 abstained** across all 32 validation queries (`npx tsx scripts/verify-recall.ts`), with **zero Fleet DB, LLM or game calls**.

This is limited, sample-specific evidence of helpful semantic recall ordering. It does not prove calibrated probabilities, generalization to all live memories, improved Nemotron play or social intelligence. The checkpoint emits a temperature-clamp warning for its 11+ option entry; this task uses exactly two, but makes no calibration claim for any option count. The helper uses probabilities only as an empirically evaluated abstention rule. It remains optional.

The service verifies the frozen validation checksum, runtime, revision, question wording, threshold, gate statistics and every model file digest before startup. Mismatched/failed certificates do not enable it. Requests are loopback-only and bounded, admit no strategy/action shape and log no player bodies. Its model is loaded offline from the pinned local artifacts. No hosted Jev endpoint, cloud credentials, auto-fine-tuning or model-provider migration was used.
